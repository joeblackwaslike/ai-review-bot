## Findings

### 1. 🟢 [P3] Cron handler does not validate IMPROVE_TARGET_REPO format

`slug.split("/")` is destructured without checking that owner and repo are both non-empty. A malformed env value passes undefined to installationOctokit and fails with an opaque error. The CLI `propose` command validates this; the cron path does not.

### 2. 🟢 [P3] Test file only: no production SAST-relevant code to audit

The only file under review is a vitest suite (src/review.test.ts). It contains no request handling, input parsing, secrets, or shell/SQL/HTML sinks, so none of the SAST vulnerability classes (injection, XSS, hardcoded secrets, path traversal, deserialization) apply. The fixtures use dummy values (`privateKey: "pem"`, `webhookSecret: "secret"`) that are clearly mocked configuration, not real credentials.

### 3. 🟢 [P3] Tests hard-code the number of Tier 1 agents in many mock chains

Many tests chain five `mockResolvedValueOnce(agentResponse)` calls followed by a summary response, and assertions like `toHaveBeenCalledTimes(5/6)` and "3 of 5 agents did not run" encode the agent count. A change to TIER1_SKILLS length would shift mocks onto the summary call. Some tests already use TIER1_SKILLS.length; consider applying that consistently via a helper. This is a maintainability concern, not a defect.

### 4. 🟢 [P3] Clock mock in budget tests not restored on failure

In the 'agent time budget' and 'partial runs cannot approve' tests, `vi.spyOn(Date, "now")` and `console.warn` spies are restored only at the end of the test body. If an assertion or `buildReview` throws earlier, the mocked clock leaks into later tests and can cause confusing cascading failures. Use `try/finally` or restore in an `afterEach` (e.g. `vi.restoreAllMocks()`).

### 5. 🟢 [P3] Severity scale mismatch in fixtures (defensive test aside)

Test at 'grounds the prompt in survivingPrior' uses `severity: "critical"` in a `PersistedFinding`, which is outside the P0–P3 scale used elsewhere. It compiles only if PersistedFinding.severity is a loose string; if so it may mask the type contract. Consider using a valid severity value unless legacy values are intentionally being tested.

### 6. 🟡 [P2] reviewCount in persisted state is not incremented

The body is rendered with `reviewCount: (state?.reviewCount ?? 0) + 1`, but the saved ReviewState writes `reviewCount: state?.reviewCount ?? 0`. The persisted count never advances, so every subsequent re-review will render the same review number in the metadata block. The next round's `reviewCount + 1` stays stuck at 2 after the first review.

### 7. 🟢 [P3] Resolved-finding tombstones and fresh findings can conflict in persisted state

Merging deduped by id lets a fresh finding win over a resolved tombstone, which is intended. However, a finding resolved this round via triage may still be re-raised by agents, since resolvedKeys only filters by title or path:line. Findings resolved by triage are filtered in mergeReviews, so this is mostly fine. A related risk: `survivingPrior` forces REQUEST_CHANGES even if the agents re-raise the same finding fresh. The finding then appears both in the 'still open' table and in the fresh findings, so it is double-reported.

### 8. 🟡 [P2] Persisted reviewCount is never incremented

The posted review body uses `reviewCount: (state?.reviewCount ?? 0) + 1`, but the new persisted state is saved with `reviewCount: state?.reviewCount ?? 0`. The stored count therefore never advances, so every re-review reads the same prior count and emits the same `ai-review:review=` value. Persist the incremented value.

### 9. 🟡 [P2] Triage and summary failures handled inconsistently (silent fallback)

`triageReReview` catches every error, including auth/config errors, and fails safe to INCREMENTAL. The log is emitted, but the user-visible review never says that triage failed, so a misconfigured auth setup can look like a normal incremental pass. Consider surfacing a notice in the review body. Separately, `generateSummary` has no try/catch in `buildReview`, so a summary failure discards all the agent work and nothing is posted.

### 10. 🟡 [P2] Persisted reviewCount never incremented

The review body uses `(state?.reviewCount ?? 0) + 1`, but the persisted newState stores `reviewCount: state?.reviewCount ?? 0` without adding 1. Each subsequent review will therefore display the same count (always 1 on the first re-review, and never advance beyond 2), so the review counter in metadata is stale.

### 11. 🟡 [P2] Resolved findings re-persisted as open when re-raised or still anchored

On a FULL/INCREMENTAL pass, byId keeps fresh findings first. Resolved tombstones are only retained if no fresh finding shares the id. That is intended, but survivingPrior open findings are also persisted unconditionally, even on a FULL pass that reviewed their files and did not re-raise them. Genuinely fixed findings that triage failed to mark resolved (e.g. the triage fail-safe returns resolved: []) stay open forever and force REQUEST_CHANGES on every future push.

### 12. 🟢 [P3] Triage schema in tests names an unsupported option risk: z.enum with ids may reject valid output and trigger fail-safe

buildTriageSchema constrains resolved to an enum of open ids. If the model returns any non-matching id, generateObject throws and the catch silently falls to INCREMENTAL with no resolved ids, so one bad id discards the whole triage decision including a valid SKIP.

### 13. 🟡 [P2] Surface failures when initializing the reaction buffer

The catch in `optionalKv()` silently converts every initialization error into a missing KV client. Running without the optional buffer is justified, but hiding why it is unavailable is not: malformed configuration or an unexpected initialization defect becomes indistinguishable from intentionally unconfigured KV. Operators can see successful cron cycles while buffered reactions are not consumed. Catch the expected unconfigured case explicitly, log the cause and degraded behavior, and propagate unexpected errors. For an accepted fallback, report something like `console.warn("improve: reaction buffer unavailable; continuing with corpus only", { error })` before returning null.

### 14. 🟡 [P2] Return a failing exit status when classification cannot complete any work

`classifyBundles()` correctly leaves failed items unclassified and reports `failedBatches`, but `cmdClassify()` only prints that summary and returns successfully. If every model batch fails and no deterministic items resolve, a scheduler or shell caller receives exit status zero despite none of the requested classification succeeding. Provider errors and schema failures are logged, but automation still treats the run as successful. After printing the summary, set a nonzero exit status when `run.failedBatches > 0 && classified.length === 0`, or throw an actionable error explaining that items remain queued and credentials/provider availability should be checked. Preserve the successful empty-queue path.

### 15. 🟡 [P2] Cover model construction for API-key and OAuth authentication

Important improvement (7/10): The supplied model tests cover pricing only, while the audit routing test mocks runAgent and therefore never exercises createAIModel. Add provider-factory tests for both providers with omitted auth, explicit API-key auth, and OAuth auth. Verify credential/baseURL forwarding, custom fetch and headers, and the OpenAI OAuth Responses path. These tests would catch regressions where local subscription runs use ambient credentials or the wrong backend despite routing tests continuing to pass.

### 16. 🟡 [P2] Test the QC judge's failure classification contract

Important improvement (7/10): The supplied QC suite tests summarization of manually supplied null verdicts, but never exercises judgeFinding. Mock model generation and verify that a successful verdict is returned, ordinary provider errors become null, and TypeError/ReferenceError propagate. Include SyntaxError and RangeError cases because their recoverability is explicitly intentional. This would prevent a regression that either aborts QC on a recoverable response failure or silently disguises a programming defect as an outage.

### 17. 🟡 [P2] Represent insufficient evidence as an unjudged QC result

When no hunk is available or the supplied code is insufficient, the judge prompt explicitly instructs the model to return `isFalsePositive: false`. The schema has no way to express that the claim could not be evaluated, so `summarize()` counts the response as judged and the report can present it as holding up. A rationale mentioning missing context does not solve this because rationales are only displayed for flagged findings. Add an explicit insufficient-evidence outcome and count those findings as unjudged, rather than allowing missing context to inflate the quality score.

### 18. 🟡 [P2] Truncated-compare tests do not verify that agents receive the full PR

Important improvement (7/10): Both truncated-compare tests can pass without a FULL review actually occurring. The SKIP case only asserts a non-null result, and the INCREMENTAL case seeds no prior findings and returns clean agent responses, so an incorrectly scoped incremental review can also produce the asserted APPROVE. Seed a distinctive file in the full PR list and a different, non-empty partial delta, then assert that buildUserMessage receives the full PR files/context rather than the partial comparison. Also assert that agents ran in the SKIP case. This would catch a regression where truncation silently excludes files from review while still approving the PR.

### 19. 🟡 [P2] Truncated INCREMENTAL regression test does not verify full review scope

The test named “ignores INCREMENTAL from triage and runs a FULL review when compare is truncated” would also pass if the implementation incorrectly took the INCREMENTAL path. Its prior findings and delta files are both empty, and all agents return no findings regardless of their input, so either path can produce a non-null APPROVE result. Assert that buildUserMessage receives the full PR file or its patch, rather than the empty delta scope. This makes the test detect the incomplete-review regression it is intended to prevent.

### 20. 🟠 [P1] Validate incremental comments against the actual PR diff

On an INCREMENTAL pass, comment validation and the returned validLinesByPath use the last-reviewed-SHA-to-head delta rather than the PR's base-to-head diff. Those diffs can have different commentable lines: a delta can include changes that revert an earlier PR change and therefore disappear from the current PR diff. Such comments pass local validation but cannot be anchored by GitHub. Keep scopedFiles for agent input, but validate and sanitize submitted comments against the full PR files already fetched.

### 21. 🟡 [P2] Preserve completed reviews when summary generation fails

After agents successfully produce findings, generateSummary is awaited without error handling. A transient provider error, exhausted quota, or invalid structured summary therefore rejects buildReview and discards the completed review instead of posting its findings. Catch summary failures and use the existing deterministic fallback text, while retaining the findings and verdict.

### 22. 🟡 [P2] Persist findings excluded by the inline-comment cap

Findings beyond the 50-comment cap are omitted from persisted state as well as from the posted review. Once lastReviewedSha advances, subsequent incremental reviews cannot carry these known issues forward or resolve them through triage; after the retained findings are fixed, the bot can approve while an overflow finding remains unresolved. Apply the cap only to presentation, and persist all discovered inline findings so overflow issues continue to affect later verdicts.

### 23. 🟠 [P1] Preserve completed findings when summary generation fails

The final generateSummary call is unguarded. If it encounters a network error, provider refusal, exhausted quota, or invalid structured output after agents have completed, buildReview throws instead of returning any of their findings. This is especially likely when the agents have already consumed the provider's rate allowance. Catch summary-generation failures separately, log the underlying error, and return the completed review with an explicit summary-unavailable notice and a deterministic summary. Presentation failure should not discard successful review work.

### 24. 🟠 [P1] Treat unavailable patches as incomplete review coverage

When raw-diff recovery fails or yields no patch for a changed file, the code logs a warning and continues without marking the review partial. If all agents return no findings from the remaining visible code, cleanDelta can still produce APPROVE and the user receives 'No issues found' despite an unreviewed file. Track files whose reviewable patches remain unavailable, include an actionable coverage warning in the posted review, and prevent automatic approval until that gap is resolved or explicitly accepted.

### 25. 🟡 [P2] Surface partial provider refusals in the posted review

Rate-limited and quota-exhausted agents are surfaced only when no agent succeeds. When at least one succeeds, those failures are excluded from both skipped and errored, so the posted review has no partial-coverage notice or provider-specific recovery instructions. Although automatic approval is correctly prevented, users cannot tell that some reviewers never completed. Include these outcomes in the partial-review notices, distinguish retryable rate limits from exhausted balance, and count them when computing partial readiness.

### 26. 🟠 [P1] Do not accept resolution decisions from a truncated delta

Critical gap (8/10): add a buildReview-level regression test where the compare response hits COMPARE_FILE_CAP and triage returns resolved finding IDs. Although the code forces a FULL review, it first marks those findings resolved and populates resolvedKeys. The full-review merge then suppresses findings at those keys even if agents detect that they remain broken, allowing an incorrect approval. When the delta is truncated, discard its resolution decisions as well as its SKIP/INCREMENTAL recommendation. The current truncation tests verify only the file-count predicate, not this safety behavior.

### 27. 🟠 [P1] Authenticate review authors before trusting review metadata

The idempotency check trusts any review body containing the configured heading and a matching SHA, without verifying who submitted it. A PR participant able to submit a review can copy the bot's heading and metadata block into their own review, causing `buildReview` to return `null` before any agents run. The same body-only identification also lets human-authored content masquerade as the bot's prior review. Fetch and validate the review author's immutable identity against the expected bot identity before using a review for idempotency or prior-own-review state.

### 28. 🟡 [P2] Preserve finding explanations in the posted review body

General findings are rendered with only severity, category, and title; their bodies and evidence never reach the author. Unanchorable inline findings likewise fall back to a title-only notice despite saying they were posted there instead. Since the summary explicitly avoids listing every finding, an actionable explanation can disappear entirely. Render the detailed explanation for general and unanchorable findings rather than relying on their titles.

### 29. 🟠 [P1] Do not let summary generation discard completed agent results

After agents have completed successfully, generateSummary makes another provider call without an error fallback. A rate limit, exhausted balance, or transient error at that point rejects buildReview and prevents all collected findings from being returned. Catch summary failures and submit a deterministic fallback summary with the completed findings; the existing fallback handles only a successful response containing whitespace.

### 30. 🟠 [P1] Reject resolution decisions from a truncated comparison

The truncation guard forces a full agent pass, but triage resolutions from the incomplete comparison are applied before that guard. Those findings become resolved tombstones and populate resolvedKeys, which then suppress matching agent findings even during the full review. Consequently, forcing FULL does not actually prevent incomplete triage data from clearing blockers. When the comparison is truncated, discard its resolution decisions as well as its SKIP/INCREMENTAL recommendation.
